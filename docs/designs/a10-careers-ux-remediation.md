## Problem Statement

The Careers surfaces do not look or behave like the rest of the platform, the employer side
never confirms a successful action, typing in the search box fires one request per keystroke,
and both forms hardcode key names and option sets that the server should own but does not
declare today. The client raised nine points after the demo. Each is verifiable in the code.
Three are broader than the brief implies and one is smaller than the brief implies.

## Scope of the server schemas, stated precisely

`listing_type_schema` and `application_schema` are **key sets for the extra fields**, the ones
that vary per role type and land in `structured_fields` and the application snapshot. They are
not whole-form definitions, and they declare string types with no allowed values.

Per seeded config: the taxonomy config declares four listing keys (`role_type`, `salary_range`,
`experience_years`, `shift`) and two application keys (`experience`, `portfolio_url`); the
hiring-partner config declares one application key (`experience`). Neither declares an enum.

The top-level fields (`title`, `description`, `location_text`, `contact_phone`, `contact_email`
on a listing; `name`, `phone`, `email`, `cover_note`, `resume_url` on an application) are
serializer fields with their own validation. `experience` is the overlap case: a valid
serializer field that also appears in the schema and is read back from the snapshot
(`my-applications/page.tsx:240-243`).

So "forms come from the server" means, precisely: **the extra structured fields render from
the schema, and Slice 4 adds allowed values so option sets become server data too.** It does
not mean every input is schema-generated, and it cannot, because the seeded `application_schema`
covers fewer fields than the form has. This distinction bounds what Slice 4 can deliver.

## UX Diagnosis

### Information hierarchy
- The card leads with employer and location; the role title is third.
- Every fact carries equal weight, and `View & Apply` is `hidden md:inline-flex` (`page.tsx:281`), so mobile loses it.
- The detail page is one block with no separation between the role, the employer and the action.
- The primary action sits in a non-sticky 380px column (`[listingId]/page.tsx:260`).

### Journey
- Mobile has no route into Careers.
- Browse and detail are separate page loads, so filters and scroll are lost.
- The status history renders in internal vocabulary.
- Withdraw gives no confirmation and no error.

### Forms
- Phone requires a hand-typed `+91`.
- The partner Contact Phone placeholder (`+91 99000 00088`) reads as a filled value. I mistook it for one during capture and hit a validation error.
- Eight fields on create, six on apply. The create form does use a two-column grid (`page.tsx:708`), so "no layout" would be wrong; what is missing is grouping and an optional-field signal.
- Option sets are literal `<option>` lists with no server counterpart.

### Validation
- Server authority plus mirrored zod is in place; the duplication is the risk and it has already drifted twice.
- Four separate status label maps: `customer/.../[listingId]/page.tsx:110-111`, `customer/.../my-applications/page.tsx:26-78`, `partner/.../listings/[listingId]/page.tsx`, `partner/.../listings/page.tsx:117-141`.
- Out-of-schema structured keys are accepted.

### Responsive
- No mobile navigation entry.
- The browse page carries sixteen breakpoint-prefixed classes, none of which restructure the search bar or the filters for small screens.
- Below `lg`, the apply panel stacks under a long description.

## Premises

1. Careers should use the M1 system, not a separate visual language. Agreed.
2. Success and failure must be visible when they happen. Agreed.
3. Typing must not cost a browse request. Agreed.
4. The server owns the extra structured fields and, after Slice 4, their allowed values. Top-level form fields stay conventional serializer fields. Agreed.
5. The fail-closed gates, "listing is not booking", and contact masking stay. Agreed.
6. Slice 1 changes frontend code only and introduces no contract change. Agreed.
7. Decompose before restyling, so the restyle lands on smaller files. Agreed.

## Job-portal principles adopted (structure, never visuals)

A consistent scannable card ordered title, employer, location, pay, posted age; a
results-and-detail split on desktop with a sticky action; a filter rail plus chips;
application tracking in readable vocabulary; pre-filled applications; and empty and loading
states that teach. Applied as information order and flow, rendered in the M1 system. No
portal's palette, type or components are copied.

## Recommended Approach

Approach A.

### Slice 1, this week: frontend only, no contract change

1. **`PhoneField`**, a fixed `+91` chip plus a ten-digit input, used in the customer apply form
   and the partner create and edit phone inputs. The server keeps `normalize_phone_number`
   (E.164, region IN) as the authority.
   - A pasted `+91 99000 00088` has the prefix stripped on entry.
   - A value that is not ten digits after stripping is refused with "Enter a 10-digit mobile number".
   - **The client keeps requiring `contact_phone`; the server field is not changed in this
     slice.** The required/optional mismatch is a backend change, so it cannot ride here.
   - The component lands in `@vsolve/ui` because that is the DRY answer the client asked for.
     It is a new export with no change to any existing component, so the blast radius is the
     package surface, not its behaviour.
2. **Success feedback.**
   - Partner: `notify()` on create, edit, submit, publish, close and subscribe, successes only.
   - Customer: an inline confirmation for withdraw to match the existing apply pattern, and a
     `role="alert"` error where `my-applications/page.tsx:90-99` currently shows nothing.
   - Failures that need recovery are **not** toasted. `packages/ui/src/toast.tsx:8-19` states
     that a toast confirms something the user just did and must not carry a failure the user
     has to act on. Failures go to the existing inline banners, and the two partner mutations
     with no `onError` at all (`action`, `subscribe`) get one. The `danger` tone the component
     documents for non-recoverable background failures is left for that case.
   - No `ToastProvider` is added to the customer app. Its deliberate inline-live-region pattern
     stays, and the success card and error `role="alert"` remain the customer's feedback.
3. **Search budget.** Split `draftQuery`/`appliedQuery` **and** `draftLocation`/`appliedLocation`,
   so both inputs are inert until the Search button, Enter or a filter change commits them. The
   query key at `listings/page.tsx:43` reads the committed pair. Add `staleTime` and
   keep-previous-data, and turn off refetch on window focus for the public list. Category pills
   keep reloading results immediately, being explicit actions.

Deliberately **not** in Slice 1: any suggestions endpoint. It needs a contract change and a

### Slice 3: visual parity

Rebuild the Careers surfaces on the M1 tokens and primitives, with the desktop split view, a
sticky apply action below `lg`, and a Listings entry in the mobile bottom nav.

**Content density, as a rendering rule rather than a copy edit.** `description` is a free-text
`TextField` on the `Listing` model (`apps/listings/models.py:33`), so the page clamps it to a
fixed number of lines with an explicit "Read more".

**Structured fields as labelled facts.** Until Slice 4 publishes labels, an interim key to
label map ships with the shared model module, so four known keys render with human labels and
any unknown key falls back to a title-cased key rather than disappearing. Slice 4 then replaces
the map with the published schema.

**Status vocabulary, enumerated** so no raw enum can leak. The server's set is exactly seven
values (`backend/apps/listings/models.py:137-144`): `SUBMITTED` → Applied, `UNDER_REVIEW` →
Under review, `SHORTLISTED` → Shortlisted, `CONTACTED` → Contacted, `REJECTED` → Not selected,
`WITHDRAWN` → Withdrawn, `EXPIRED` → Closed. There is no `HIRED` and no `VIEWED` on the server.
Event kinds map into the same vocabulary, so `CONTACT_REVEALED` reads as "Your contact details
were shared with the employer" rather than as an enum pair. `my-applications/page.tsx:106`
currently filters the closed tab on a `HIRED` literal that cannot occur, and `:54` defines a
label for it; Slice 1 removes both.

### Slice 4: server as the source of truth

In this order:
1. **Align the key names first.** Update the seed and both forms to the schema's names, and fix
   the application drift (`portfolio_url` in the schema versus `resume_url` in the serializer)
   so the two agree. Data migration for existing rows. Enforcement cannot land before this.
2. **Reconcile `application_schema` with the real application fields.** The seeded version
   covers two keys, the hiring-partner variant one, while the form has six. Decide which extras
   are genuinely schema-driven.
3. **Introduce allowed values.** Each seeded property is a bare string type today, so option
   sets are not server data at all. Add enums for the fields that have fixed choices, which is
   what lets the client stop hardcoding `<option>` lists.
4. Publish both schemas through a proposal, Django, and a client regeneration. Additive.
5. Render the extra structured fields, their labels and their option sets from the published schema.
6. Enforce `structured_fields` against the schema, keeping the existing size bounds.
7. Publish the filter taxonomy so the seven client constants become server data.
8. Optional, only if the client asks: a debounced suggestions endpoint with its own contract change.

## Success Criteria

- Typing 20 characters with keys at least 300 ms apart, in either the keyword or the location
  box, fires zero browse requests. Pressing Search fires exactly one. Switching tabs and
  returning fires none.
- Partner create, edit, submit, publish, close and subscribe each produce a visible confirmation;
  a failing one leaves a message in place rather than a toast.
- Customer withdraw confirms on success and shows a `role="alert"` message on failure.
- The phone field accepts ten digits and stores E.164; a pasted `+91` value is handled.
- The Careers file set contains no `slate-` or `indigo-` utility; `amber-`, `emerald-` and
  `rose-` reach the DOM only through `Badge` tones; and a side-by-side against
  `/catalog/technician` matches colour family, radius, shadow and primitives.
- No Careers file above 250 lines; one status vocabulary in the codebase, and no raw status
  enum or event kind rendered to a user.
- The extra structured fields render with labels and, after Slice 4, with their option sets from
  the published schema; a payload with an out-of-schema key is refused server-side.

## Reviewer Concerns

Three adversarial review rounds ran against this document, each with an independent reviewer and
no access to this conversation. Quality scores were 6/10, 6/10, 6/10. Round 1 produced 18
findings, round 2 produced 12, round 3 produced 9, and every factual claim the reviewers tested
against the code was either confirmed or corrected in this revision. The loop stopped at the
three-iteration cap, so the following remain open rather than resolved:

- **The ceiling of "server-driven forms" is lower than the phrase suggests.** The seeded schemas
  declare two keys, with no allowed values, against forms of six and eight fields. Slice 4 can
  make the extra fields and their option sets server-owned. It cannot make every input
  schema-generated without redesigning the serializer fields, which is out of scope here. The
  client should hear that bound before the work starts, or the deliverable will look partial.
- **Whether the customer side needs a toast at all** is settled here as no, on the grounds that
  the app deliberately uses inline live regions and the client's point 1 is about the employer
  side. A reviewer argued point 1 was written about users generally. If the client meant both
  audiences, Slice 1 gains a customer toast and loses a deliberate pattern, and that is worth
  one question rather than an assumption.
- **Slice 3's labelled structured fields depend on an interim key to label map** that ships
  before the schema that would generate it. That is a deliberate shortcut, and it should be
  deleted in Slice 4 rather than left to drift.
