# API, Events and Background Jobs

## API conventions

- Base path: `/api/v1`
- JSON uses one documented naming convention.
- All timestamps are UTC ISO 8601.
- Money uses integer paise.
- Pagination is cursor-based for operational lists.
- Mutating endpoints accept an idempotency key where retries are possible.
- Validation errors are field-addressable.
- Every error includes a stable machine code and safe customer message.
- OpenAPI is generated by Django and used to generate the TypeScript client.

Example error:

```json
{
  "error": {
    "code": "SLOT_NO_LONGER_AVAILABLE",
    "message": "That time is no longer available.",
    "fields": {},
    "retryable": true,
    "trace_id": "..."
  }
}
```

## Quote transaction

Quote generation:

1. Load active service variant and rate.
2. Validate scope/options.
3. Validate duration bounds.
4. Calculate service lines.
5. Calculate configured platform fee.
6. Calculate taxes by taxable component.
7. Store immutable quote and lines.
8. Return expiry/version.

The frontend never reconstructs totals independently.

## Capacity hold transaction

Scheduled:

1. Validate checkout session, cart snapshot and quote.
2. Find eligible candidates from published committed availability.
3. Lock candidate schedule/reservation scope.
4. Re-check full occupied-range overlap.
5. Create short-lived `CapacityHold` and held `PartnerReservation`.
6. Return hold expiry, payment-start deadline, `server_now` and safe provider representation.

Instant is reversed per ADR-028/029
([doc 11 §2–§3](./11-payment-first-instant-and-cancellation-policy.md)):

1. Run a lock-free eligible-pool existence pre-check. An empty pool blocks checkout before any charge.
2. Take payment; authoritative capture creates `Booking(status=PAID_UNASSIGNED)`.
3. Rank, acquire the Redis Instant lock and create `JobAssignment(ASSIGNED_PENDING_ACK)`.
4. On explicit Partner acknowledgement, perform steps 3–6 above transactionally and release the exact
   address and contact to the Partner.
5. On no acknowledgement, release the lock, exclude that Partner and reassign; on ceiling, follow the
   `NO_PARTNER_CONFIRMED` recovery path (reschedule → bounded retry → refund).

Database constraints are the final race-condition guard.

## Checkout transaction

Before payment:

1. Validate customer owns the cart and checkout session.
2. Revalidate quote.
3. Revalidate every capacity hold.
4. Create a pending Order/payment intent idempotently; do not create a Booking yet.
5. Create payment attempt.
6. Return payment-provider action.

On authoritative payment success:

1. Persist webhook event idempotently.
2. Mark payment/order captured.
3. Create each Booking exactly once from the checkout snapshots.
4. Convert holds into confirmed reservations linked to those Bookings.
5. Create outbox events.
6. Return quickly.
7. Let workers deliver notifications/invoices.

On payment failure/expiry:

- Release holds.
- Mark attempt failed/expired.
- Unlock/retain the cart for a bounded recovery period.

## Provider selection policy

Eligibility gates:

- Partner active
- KYC approved
- Required skill/service enabled
- Within service area/distance
- Available for complete interval
- No active overlapping reservation
- Not suspended or blocked for the customer

Ranking may include:

- Distance/arrival estimate
- Relevant rating
- Completed jobs
- Fairness/workload
- Customer preference or prior booking

Ranking weights are versioned and logged. They must never override eligibility.

## Required jobs

| Job | Trigger | Behaviour |
|---|---|---|
| Expire capacity hold | ETA/scheduler | Release reservation idempotently |
| Reconcile pending payment | Scheduled | Query provider and repair local state |
| Deliver outbox | Continuous | Publish pending domain events |
| Send notification | Event | Retry with backoff and delivery log |
| Generate invoice | Payment/completion | Produce immutable invoice |
| Expire OTP | Time-based | Reject stale challenge |
| Start overtime state | Work deadline | Mark/notify without silent charge |
| Clean abandoned carts/checkouts | Scheduled | Expire non-financial carts and release checkout holds |

All tasks:

- Are idempotent
- Have bounded retries
- Use exponential backoff where appropriate
- Record terminal failure
- Include trace/correlation identifiers
- Can be replayed safely by operations

## Real-time transport

For Milestone 1:

- Use bounded TanStack Query polling or server-sent events for customer status presentation.
- WebSocket/realtime transport is optional.
- The database remains authoritative.
- Receiving a real-time message causes a refetch; it does not directly mutate irreversible state.
- Dispatch never depends on an open browser connection.
