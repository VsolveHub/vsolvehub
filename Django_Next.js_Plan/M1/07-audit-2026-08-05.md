## Blocking defects found in the uncommitted work (now fixed)

### A0 — The Operations shell does not compile

`frontend/apps/admin/features/session/operations-shell.tsx`

```
(48,20) TS2552: Cannot find name 'usePathname'
(58,16) TS2304: Cannot find name 'Link'
(69,17) TS2304: Cannot find name 'Link'
  47:10  error  'WorkspaceNav' is defined but never used
```

Two missing imports (`next/navigation`, `next/link`) — and `WorkspaceNav` is **never rendered**.
So the four new Operations pages under `/operations/*` are unreachable by any link, which is the
same navigation defect the plan already flagged for the Customer and Partner apps.

**Fixed.** Imports added, `<WorkspaceNav />` mounted between the header and `<main>`. All six admin
routes wrap themselves in `OperationsShell`, so the nav appears on every one.

### A1 — FE-15's own privacy gate is red

`frontend/apps/customer/features/addresses/storage-boundary.test.ts:137`

**Two** false positives, not one. The regex `/\berror\b(\s*\.\s*\w+)?/g` matched the `error` in
`console.error(` itself, and — once that was excluded — the tag string
`"[account-error-boundary]"`, where `error` sits between two hyphens and so has word boundaries on
both sides. The production code (`app/(flow)/account/error.tsx:30`) logs `error.digest ??
"no-digest"` and was always fine. **The guard was wrong, not the code** — and it had clearly never
been run, in either direction.

**Fixed.** The rule now scans only a console call's *arguments*, with single- and double-quoted
literals stripped. Template literals are left intact: `${error.message}` inside one is live code
and is exactly the leak the rule exists to catch. Verified red against a deliberate bare-`error`
log before being accepted green.

Including all of `apps/fulfilment`, `tests/fulfilment`, the BE-07 hardening, FE-15 and FE-16.

**Fixed.** Committed as `bc17926` (backend + contracts) and `10903d7` (frontend).

### A3 — The backend gate is unverifiable right now

**Resolved.** The user started the containers; both are healthy on 15432/56379. The gate then ran

### The pattern worth remembering

**Publish a command, withhold its key.** It happened three times:

1. `recovery_action` returned `PAYMENT_REQUIRED` while the group published neither `checkout_id`
   nor `checkout_version` (proposal 0011).
2. Every 1.16.0 Customer command is keyed by `booking_id`, and the only projection listing a
   Customer's units published no `booking_id` (fixed in the same release).
3. The four Operations dispatch commands shipped in 1.15.0 with no caller anywhere.

Each time the backend was "done" and the capability was unreachable. The check that catches it is
cheap: after publishing a command, ask what a client must already hold to call it, and whether any
published projection actually carries that.

**A guard that has never been run red is not evidence.** FE-15's privacy scanner and the schema
tests both passed while failing to check anything, or while failing the one file that was
correct. Every regression added in S3 was verified red before being accepted.

**Uncommitted work is invisible work.** This audit began because 3,100 lines of tested domain
code were sitting in an uncommitted working tree, so every status document in the repo was wrong.
